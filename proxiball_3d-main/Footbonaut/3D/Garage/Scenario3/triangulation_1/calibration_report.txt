Calibrate the extrinsic parameters (rotation R and translation t) of 4

Inputs:

2.1 World Coordinate System (User-Defined)

Origin: North-East corner (0, 0, 0)

- Y-axis: East (0) → West (298 cm)

2.2 Camera Coordinate System (OpenCV Standard)
----------------------------------------------
- X-axis: Points right in image
- Y-axis: Points down in image
- Z-axis: Points forward along optical axis (into scene)

2.3 AprilTag Corner Ordering
----------------------------
Detector returns corners in order: [c0, c1, c2, c3]
Canonical ordering: Top-Left, Top-Right, Bottom-Right, Bottom-Left
  - c0 = Top-Left (corner nearest white square in tag pattern)
  - c1 = Top-Right
  - c2 = Bottom-Right
  - c3 = Bottom-Left

Important: Corner order is determined by tag's internal pattern, NOT physical
orientation. Tags can be rotated, but detector always returns corners in the
same canonical order relative to the tag's encoded orientation.

3. CALIBRATION METHODOLOGY
================================================================================

3.1 Libraries and Dependencies
------------------------------
- OpenCV (cv2): Version with ArUco/AprilTag support
- NumPy: Array operations
- Python: 3.x

Key OpenCV Functions Used:
- cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_APRILTAG_36h11)
- cv2.aruco.ArucoDetector()
- cv2.aruco.DetectorParameters()
- cv2.solvePnPRansac() - RANSAC-based PnP solver
- cv2.solvePnP() - Refinement after RANSAC
- cv2.Rodrigues() - Convert rotation vector ↔ matrix
- cv2.projectPoints() - Project 3D → 2D for verification

3.2 Input Data Preparation
--------------------------
Intrinsics (unified_intrinsics.json):
  - Camera matrix K (3×3): Focal lengths (fx, fy) and principal point (cx, cy)
  - Distortion coefficients D (5,): Radial and tangential distortion
  - Resolution: 1920×1080
  - Source: Scaled from cam0_intrinsics.npz (1.5x)

3D Tag Coordinates (Dimensions.txt):
  - 24 AprilTags (IDs 0-23)
  - Each tag: 4 corners × (X, Y, Z) coordinates in cm
  - Tag size: 21.5 cm × 21.5 cm (physical dimension)
  - Measured with ruler, relative to NE corner origin
  - Corner ordering: c0, c1, c2, c3 matching detector output

3.3 Detection and Correspondence Collection
-------------------------------------------
For each camera:
  1. Load all images from camera folder (50 images per camera)
  2. Convert to grayscale
  3. Detect AprilTags using cv2.aruco.ArucoDetector
  4. For each detected tag:
     - Look up 3D coordinates from Dimensions.txt
     - Extract 2D image coordinates from detector
     - Collect as object points (3D) and image points (2D) pairs

Tags detected across cameras:
- camNorth: 15 tags (1, 2, 3, 4, 6, 11-15, 17, 19, 20, 21, 22)
- camEast:  11 tags (2, 3, 4, 6, 10, 12-15, 21, 22)
- camSouth: 15 tags (5, 7-10, 13-15, 17-23)
- camWest:  10 tags (0, 5, 7-9, 16, 17, 19-21)

Multi-camera shared tags:
- Tag 21: visible in ALL 4 cameras (floor tag)
- Tags 13-15, 22: visible in 3 cameras
- Tags 17, 19, 20: visible in 3 cameras

3.4 PnP Calibration with RANSAC
-------------------------------
Algorithm: cv2.solvePnPRansac()

Parameters:
  - objectPoints: N×3 array of 3D world coordinates (cm)
  - imagePoints: N×2 array of 2D pixel coordinates
  - cameraMatrix: K (3×3)
  - distCoeffs: D (5,)
  - reprojectionError: 8.0 pixels (RANSAC threshold)
  - flags: cv2.SOLVEPNP_ITERATIVE
  - iterationsCount: 1000

Output:
  - rvec: Rotation vector (3×1) - axis-angle representation
  - tvec: Translation vector (3×1) - world origin in camera frame
  - inliers: Indices of inlier points (outliers rejected)

Refinement:
  After RANSAC, used inlier points only to refine rvec and tvec with
  cv2.solvePnP(useExtrinsicGuess=True) for improved accuracy.

3.5 Camera Position Calculation
-------------------------------
Convert rvec to rotation matrix R using cv2.Rodrigues():
  R, _ = cv2.Rodrigues(rvec)

Calculate camera position in world frame:
  C = -R^T × t

Rationale: [R|t] transforms world → camera coordinates.
For a point Pw in world frame:
  Pc = R × Pw + t
The camera center C satisfies: 0 = R × C + t, hence C = -R^(-1) × t = -R^T × t

5. INVESTIGATION AND ANALYSIS
================================================================================

5.1 Initial Hypothesis: Corner Ordering Mismatch
------------------------------------------------
Tested whether tag corners in Dimensions.txt were ordered differently than
detector output due to tag rotation during placement.

Result: User confirmed corners were measured to match detector IDs (c0=blue,
c1=green, c2=red, c3=yellow in debug visualization). No reordering needed.

5.2 Second Hypothesis: Z-Axis Sign Convention
---------------------------------------------
Test: Negated all Z coordinates in tag measurements.

Result: No improvement. Error remained ~460 cm for camEast.

5.3 Shared Tags Analysis
------------------------
Calibrated camEast using different tag subsets:

Floor tags ONLY (21, 22):
  Position: (211, 10, -235) cm
  Expected: (230, 7, 228) cm
  Error: 463 cm
  Observation: X, Y close, Z has opposite sign

Wall tags ONLY (all except 21, 22):
  Position: (334, 618, 166) cm
  Expected: (230, 7, 228) cm
  Error: 623 cm
  Observation: Completely wrong

Conclusion: Floor tags give consistent X, Y but flipped Z. Wall tags give
entirely incorrect results. This suggests a fundamental coordinate system
interpretation issue rather than a simple sign flip.

5.4 CRITICAL TEST: Triangulation Round-Trip Verification
--------------------------------------------------------
Test Procedure:
  1. Select a known 3D point: Tag 21 center at (222.55, 171.75, 4.0) cm
  2. Project to all 4 cameras using calibrated extrinsics
  3. Triangulate back from 2D projections using camera pairs
  4. Compare triangulated 3D position with original

Results:
  camEast + camNorth triangulation:
    Result: (219.4, 174.3, 7.7) cm
    Original: (222.55, 171.75, 4.0) cm
    Error: 5.5 cm

  camEast + camSouth triangulation:
    Result: (220.5, 170.8, 3.8) cm
    Original: (222.55, 171.75, 4.0) cm
    Error: 2.3 cm

Conclusion: Triangulation accuracy is EXCELLENT (2-5 cm error out of 222 cm
scale, which is 1-2% relative error). This proves the extrinsics [R|t] are
mathematically correct for the intended purpose (3D reconstruction).

6.2 Camera Position Discrepancy
-------------------------------
✗ Calculated camera positions do not match expected physical measurements
✗ Some positions are outside room bounds or below floor (physically impossible)

Root Cause Analysis:
The discrepancy suggests a coordinate frame interpretation issue between:
  1. The world coordinate system defined in Dimensions.txt
  2. The coordinate system implicitly assumed by OpenCV's solvePnP
  
The formula C = -R^T × t is standard for camera position calculation, but
the resulting positions are in the "world frame as interpreted by solvePnP",
which may differ from the user's intended world frame due to:
  - Handedness conventions (right-hand vs left-hand coordinate systems)
  - Axis orientation conventions
  - Viewing direction assumptions

However, this does NOT affect the validity of [R|t] for projection and
triangulation, as demonstrated by the round-trip test.

6.3 Practical Implications
--------------------------
For 3D Ball Tracking:
  ✓ Use extrinsics.json as-is
  ✓ Ball 3D coordinates will be accurate in the "tag coordinate frame"
  ✓ If needed, apply a coordinate transformation to convert to desired frame
  
The extrinsics enable:
  - Accurate projection: 3D world → 2D image (forward projection)
  - Accurate triangulation: Multiple 2D observations → 3D world (ray intersection)

6.4 Recommendations
------------------
1. ACCEPT the calibration results for ball tracking
2. When interpreting ball 3D coordinates, be aware they are in the "tag frame"
3. If physical camera positions are needed, investigate coordinate transform
   - May require additional constraints or reference measurements
   - Not critical for ball tracking functionality

8.3 Coordinate System Ambiguity
-------------------------------
The mismatch between calculated and expected camera positions highlights a
fundamental ambiguity in coordinate system conventions. This is a known issue
in computer vision when interfacing between:
  - User-defined measurement frames (physical space)
  - Camera coordinate conventions (OpenCV standard)
  - Mathematical conventions (solvePnP implementation)

Future work could resolve this through:
  - Explicit coordinate frame transformations
  - Validation against known reference points
  - Photogrammetric bundle adjustment with ground control points

## BLM Firmware (control_14_full.ino — deployed 2026-08-13)

- **control_14 fixed the crawling yaw.** `control_13`'s idle loop measured 40.0 ms, so its 25 ms ESC ramp gate fired on EVERY iteration and a cooperative `AccelStepper` — one step per `run()` at most — was capped at 25 steps/s. Yaw took **37 s** for a 5° move. control_14 writes a duty only when it changed, and paces the ramp at `RAMP_INTERVAL_MS = 200` / `RAMP_STEP_US = 5` (deliberately the 25 µs/s control_13 *actually* produced, not its faster nominal rate). Idle loop is now 2.8 ms and the same move takes **585.8 ms**, matching the AccelStepper triangular profile prediction to 0.5%.
- The cause was `writeMicroseconds` → `ledc_update_duty`, which actively waits for the PREVIOUS duty update to latch. Two back-to-back writes per iteration cost two 50 Hz PWM periods. Spacing them out does not ration that stall, it **removes** it: yaw during a real wheel ramp measured 586.2 ms against 585.8 ms idle. No task/MCPWM rework is needed.
- Full write-up, evidence and acceptance: `docs/superpowers/specs/2026-08-13-control-13-ledc-loop-diagnostic-design.md`. Contract tests: `tests/test_control_14_esc_ramp_contract.py` (the projection test proves reverting the three intended edits reproduces control_13 byte-for-byte).
- **`blm_bridge.COMMISSIONED_FIRMWARE` is the acceptance list**, and extending it is a deliberate act. A firmware not on it leaves the desktop LAUNCHER panel reading `UNVERIFIED`, which is the correct answer for a generation nobody has accepted.
- Inherited from control_13: `INFO | FW:` identity, unconditional 4 Hz USB actual-RPM telemetry while IDLE, no blocking `delay(50)` in `info`, and the BLE fix (no `startAdvertising()` inside `onConnect`). Command grammar, 921600 baud, pins, limits and the state machine remain control12-compatible.
- Rollback references, both pinned and immutable: `control_12_full.ino` SHA-256 `eefb35acce89f5f1467dab26865b90394e4f880127718c2697cd4924c51b660e`, `control_13_full.ino` SHA-256 `54367d26e9dee54283beba08f0d41297ddacaae2538b296349f0b00eb946049f`. An ESP32 clean build is NOT byte-reproducible, so rollback is defined by source SHA + toolchain (Arduino-ESP32 core 3.3.7) + live identity, never by a cached `.bin` hash.
- **Measured on the rig 2026-08-13 and not yet acted on:** commanding 300 RPM produces a plateau of L≈368 / R≈372 (peak 399) against the 400 RPM fire gate — the setpoint mapping is ~23% high. Left and right diverge during spin-up (L=3 vs R=125 at 6.2 s) and match within 2% only at plateau, so a shot during spin-up imparts spin. `stop` needs ~20 s to bring the wheels to rest; it releases the flywheels rather than killing them.
- ARM and FIRE have not been exercised on control_14.

### Commands
- `set v h wl wr` — aim (angles clamped ±30°) + set wheel RPMs
- `shoot` — fire (RPM gate: both wheels ≥400 RPM)
- `reload` — retract → dispense → ball detect (or 10s timeout) → IDLE; also centers + spins down
- `stop` / `center` / `setzero` / `info`
- Manual jog: `jv<steps>`, `jh<steps>`, `jf<steps>` (pusher), `js<0-180>` (servo angle)
- Live tuning (no reflash): `jsset<val>`, `jfspeedset<val>`, `jfaccelset<val>`
- `info` reports: angles, RPMs, feeder state, limit switch states (Front/Back/Ball), live config

### State machine
- IDLE → `reload` → RETRACTING → (back limit LOW) → DISPENSING → (ball limit LOW or 10s timeout) → IDLE
- IDLE → `shoot` → SHOOTING → (RPM ≥ 400) → pusher fwd → (front limit LOW) → IDLE

## Pose Backends
- `--pose-backend yolopose` — YOLO11m-Pose, 6.2x faster (6.2ms TRT vs 38.5ms MMPose per image). **VALIDATED on live arena cameras 2026-04-03.**
- `--pose-backend mmpose` — RTMDet-m + RTMPose-m (original, slower but slightly more keypoints). **Licence warning (2026-07-30): this is NOT a commercially clean path.** MMPose code is Apache-2.0, but every published RTMPose checkpoint is `pt-aic-coco` — pretrained on AI Challenger, which is research-only. The clean Apache-2.0 target is **RTMO** (`configs/body_2d_keypoint/rtmo/coco/`, already in the installed MMPose: COCO-only training, YOLOX-COCO backbone init), which is additionally one-stage and bottom-up. Not yet exported or benchmarked.

### 2026-05-29 — Projector goal-game root cause + camera upgrade plan
- **Root-caused the projector goal game's near-zero scoring (NOT broken calibration).** The "geometry never agrees" telemetry (median ~1400 px reproj, camEast+camNorth ~48,600 px, 0/14,604 frames <200 px) is a **one-line units bug** in `proxiball_3d-main/projector/goal_target_game_multicam.py`: it builds `proj_mats[cam] = K @ e["P"]` (pixel-space) but feeds **normalized** undistorted obs into `robust_triangulate_ball` — the canonical viewer correctly uses bare `extr[cam]["P"] = [R|t]`. **Proven** on real `Remounted_West_East/` files: correct pairing → 0 px, buggy pairing → 3369 mm / 611–2.9M px. ### 2026-08-13 — control_14: the crawling yaw was a 40 ms cooperative-loop stall
- **Measured, not guessed.** `control_13`'s idle loop period was **40.0 ms** (19 intervals, min 39.835, max 40.182, stdev 0.108 ms). The probe needed no diagnostic firmware: `loop()` takes at most one command per iteration and the RX ring holds 256 bytes, so `b"info\n" * 20` in ONE write makes the gap between `INFO | FW:` lines equal to one loop period. It landed on the `n=7` divisor the passive 250 ms telemetry gate had already bracketed (39.98 ms) to within 0.04% — two unrelated measurements agreeing.
- **Cause:** `escLeft/escRight.writeMicroseconds()` reach `ledc_update_duty`, which actively waits for the PREVIOUS duty update to latch. Two back-to-back writes per iteration = two 50 Hz PWM periods = 40 ms. A 25 ms ramp gate inside a 40 ms loop therefore fired EVERY iteration, and `AccelStepper` emits at most one step per `run()` — so both aim axes were capped at 25 steps/s. Observed 18.8. The firmware was rewriting the value 1000 forty times a second and paying its whole loop for it.
- **Fix (`control_14`):** write a duty only when it changed, and pace the ramp at 200 ms / 5 µs instead of 25 ms / 1 µs. 5 µs per 200 ms is 25 µs/s — deliberately the rate control_13 *actually* produced, not its nominal 40 µs/s, since restoring the nominal would spin the wheels up 1.6× faster than the operator has ever seen. Ramp rate, endpoints and the 1000 µs rest value are otherwise untouched.
- **Results:** idle loop 40.0 → **2.8 ms**; yaw 5° (694 steps) 37 000 → **585.8 ms**, which matches the AccelStepper triangular-profile prediction (0.589 s) to 0.5% — the axis runs exactly as configured, so the bottleneck is gone rather than reduced.
- **The predicted residual did not exist.** The design expected a 40 ms stall five times a second during a wheel ramp. Measured under a real ramp, yaw took **586.2 ms against 585.8 ms idle**. Because the LEDC wait is for the *previous* update, spacing writes out removes the stall instead of rationing it. **Options C and D — moving the duty update onto a task or MCPWM — are not needed.**
- **Verification:** 10 contract tests in their own file, all 9 mutations caught by the intended test (including a weakened fire-RPM gate and an unrelated edit in the untouched region). The strongest is a projection: reverting the three intended edits must reproduce `control_13` byte-for-byte. Compiled against core 3.3.7, no sketch-level warnings, 1 123 186 bytes vs control_13's 1 123 198, identical globals. Driver was the arduino-cli **1.4.1** bundled in the IDE 2.3.8 AppImage, not the 1.5.1 recorded on 2026-08-11.
